How to build a developer portfolio website: what to include, what to cut, free hosting, and the three-second test recruiters actually apply

By Pranjul RathourUpdated 2026-09-240 questions answered1,400 words

Key takeaways

  • {'A portfolio site exists to answer three questions in ten seconds': 'what do you build, is it real, how do I reach you.'}
  • Three to five projects written up properly beat ten projects listed as bullet points.
  • Every project page needs the problem, the decision, a demo or screenshot, and what you would do differently.
  • Free static hosting (GitHub Pages, Netlify, Vercel's free tier, Cloudflare Pages) is enough; do not pay for hosting a portfolio.
  • Update it after every project or talk, not on a schedule; a stale portfolio is worse than a short one.

What should a developer portfolio website include?

A home page that states what you build in one sentence and links everywhere else. Three to five project write-ups, each with the problem, the decision you made, a demo or screenshot, and what you would do differently. An about section that is two paragraphs, not a biography. A contact method that is one click away. Talks or writing if you have them. Nothing else. The whole site should answer what do you build, is it real, and how do I reach you, inside ten seconds of landing.

How do I write a project page that gets read?

Problem in one sentence: who had it and what it cost them. The decision you are proud of, in three sentences, including the trade-off. A demo video or three screenshots, never a wall of code. What you would do differently now, which shows growth more than any feature list. A link to the repository and, if it exists, a live demo. Skip the tech stack badge wall at the top; put it at the bottom if at all. A reader should understand the project without opening the code.

Which projects should I put on my portfolio?

Three to five, chosen for range and depth, not for count. One that solved a real problem for a real person. One that shows a technical decision you can defend for twenty minutes. One that is live and usable right now. Cut anything that is a tutorial clone, a copy of a template, or unfinished. A portfolio with three strong projects reads as more capable than one with twelve thin ones, because reviewers judge by the best page they see, not the total.

What should I leave off my portfolio?

Certificates, unless a project sits behind them. A skills matrix with progress bars, which nobody trusts. Every course you have completed. Tutorial clones with no changes of your own. A blog if you are not going to keep writing, better a single pinned post than an abandoned feed. Stock photography. A dense biography above the fold. The test is simple: does this page help someone decide to talk to you in the next thirty seconds; if not, cut it.

Where should I host a portfolio for free?

GitHub Pages for a fully static site, free forever on a public repository, with a custom domain supported [2]. Netlify and Vercel's free tiers for a site with a build step, also generous and free for personal use [3]. Cloudflare Pages as another free, fast option [4]. A .dev, .me or .in domain costs a small yearly fee if you want one; the hosting itself should never cost anything for a personal portfolio. Avoid managed website builders with monthly fees; a static site is simpler, faster and free.

How fast and accessible should it be?

Fast enough that it loads before the recruiter's attention moves on: a static site with optimised images and no heavy frameworks for a simple portfolio easily hits good Core Web Vitals scores [1]. Accessible enough that a screen reader can navigate it: real headings, alt text on images, sufficient colour contrast, keyboard-navigable links [5]. Neither takes more than an afternoon to get right, and both are things a recruiter or organiser will notice without naming, as a site that either feels solid or feels broken.

How do I keep it updated without it becoming a chore?

Update it the moment something changes: a project ships, a talk happens, a link breaks. Do not schedule quarterly overhauls, which is how portfolios go a year stale. Keep the write-up template from this page in a notes file so a new project page takes twenty minutes, not a weekend. Delete a project the moment you would not want it asked about; an outdated portfolio actively works against you, so removing is as valid an edit as adding.

What mistakes do developer portfolios make?

A home page with no clear statement of what you build. A skills wall that reads like a résumé keyword dump. Ten projects, all thin. Broken links to deleted repositories or dead demos. No way to contact you without hunting. A design so custom it is confusing to navigate. Copy-pasted README text with no framing for a human reader. Every one of these is fixed by the ten-second test: would a stranger know what to do next.

Developer portfolio interview questions

"Walk me through a project on your site" is the most common opener once a recruiter has read it, so every project page should survive twenty minutes of follow-up questions. Prepare the decision, the trade-off, the failure and the fix for each of your three to five projects before the interview, not during it. The portfolio's job is to earn this question; your job is to answer it well.
